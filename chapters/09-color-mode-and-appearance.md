## Add color mode support

In Chakra UI v3, color mode is provided through `next-themes`. The Chakra CLI can add the provider and helper components to a project:

```sh
npx @chakra-ui/cli snippet add color-mode
```

The generated provider composes Chakra's `ChakraProvider` with the theme provider. Use that shared provider at the root of the React tree, following the files created in your project. If the CLI creates TypeScript files but your project uses JavaScript, convert the generated files to JSX and remove type annotations rather than copying TypeScript into a JavaScript app.

The color mode helpers include a hook for reading or changing the current mode and a button for switching between light and dark. Use the generated helper instead of importing removed v2 color mode hooks from Chakra.

## Prefer semantic colors

Chakra's semantic tokens describe the role of a color and adapt to the active mode. Use them for common surfaces, text, borders, and status messages.

```jsx
import { Box, Heading, Text } from "@chakra-ui/react"

export function AppearanceCard() {
  return (
    <Box bg="bg.panel" color="fg" borderColor="border" borderWidth="1px" p="5" rounded="lg">
      <Heading size="md">Appearance</Heading>
      <Text color="fg.muted" mt="2">
        This panel uses values that adapt to light and dark mode.
      </Text>
    </Box>
  )
}
```

Tokens such as `bg.panel`, `fg`, `fg.muted`, and `border` can adapt without a separate conditional on every component. Define custom semantic tokens for project-specific meaning, as shown in the theme chapter.

## Add a mode switch

Import the color mode button generated by the snippet and place it in a suitable location:

```jsx
import { ColorModeButton } from "./components/ui/color-mode"

export function SiteHeader() {
  return (
    <header>
      <h1>Account settings</h1>
      <ColorModeButton />
    </header>
  )
}
```

The relative import assumes the page and generated file are both inside `src`, with the generated file in `src/components/ui/color-mode.jsx`. Adjust the path if your project structure differs. Use a button with an accessible name, and make its icon communicate the action or current mode clearly.

The snippet's provider supports a default mode. Set it to `light`, `dark`, or `system` based on the product decision. Respecting the system preference is a useful default; storing a user's explicit choice lets it remain consistent on later visits.

## Use a dark-mode override sparingly

For an isolated exception, Chakra provides the `_dark` condition:

```jsx
<Box bg="white" color="gray.900" _dark={{ bg: "gray.900", color: "gray.50" }}>
  A one-off surface with explicit mode values
</Box>
```

For repeated interface colors, prefer semantic tokens. Repeating `_dark` on every panel makes the theme harder to change and easier to apply inconsistently.

## Avoid a flash or hydration mismatch

With server rendering, the server may not know the saved browser color mode. A component that renders different text or markup based on the mode can briefly disagree with the first client render. Prefer CSS-driven semantic tokens for ordinary color differences. When a component must read the mode in an SSR app, use the client-only pattern described in Chakra's color mode guidance.

Test the page in light and dark mode. Check that:

- Text and controls remain readable.
- Borders and focus rings are visible.
- Status meaning is not communicated by color alone.
- Images and illustrations still fit the active background.
- The selected mode persists after reloading the page.

## Practice

1. Add the generated color mode provider to a Vite app.
2. Place the color mode button in the page header.
3. Replace explicit light and dark values with semantic tokens where possible.
4. Check a form error and focus ring in both modes.
